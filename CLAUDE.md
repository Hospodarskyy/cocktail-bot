# Cocktail Recommender Bot — Project Handoff Document

## Project Overview

A Telegram-based cocktail ordering system for home parties. Born from a personal hobby (bartending tools + frequent guest visits), built as a semester-long MLOps university course project. Dual goals: satisfy course requirements and build something genuinely usable.

**Core idea:** guests order cocktails through Telegram like ordering at a real bar — getting personalized recommendations, discovering new drinks, and having a conversational experience — while the host (admin) gets recipe notifications, inventory management, and reduced manual involvement during parties.

---

## System Roles

**Guest** — interacts via a dedicated Telegram bot (`@bartenderrrr_bot`). Can onboard (describe preferences), get personalized recommendations, place orders, optionally specify preferences per order (e.g. "not too bitter").

**Admin (host)** — interacts via a separate Telegram bot (`@bar_admin_bot`). Manages inventory, receives automatic order notifications with full recipes, views shopping lists, sees active orders.

**Why two separate bots:** simpler UX, cleaner separation of concerns, easier to reason about each bot's command set. Both bots talk to the same FastAPI backend and PostgreSQL database — no duplicated business logic.

---

## Architecture (current + target state)

```
Guest Bot (Telegram) ──┐
                        ├──► FastAPI ──► PostgreSQL (+pgvector)
Admin Bot (Telegram) ───┘         │
                                  ├──► Amazon Bedrock (LLM + image gen) [future]
                                  ├──► Redis (async events) [future]
                                  └──► S3/MinIO (training data, model artifacts)

Airflow ──► exports data from PostgreSQL ──► MinIO/S3 (training dataset)
```

Long-term target architecture (from design doc, not yet implemented): AWS-based with RDS PostgreSQL+pgvector, ElastiCache Redis, Amazon Bedrock, SageMaker, S3, ECS Fargate. Microservices: Bot Gateway, Admin Service, User Service, Order Service, Recipe Service, Recommendation Service, Image Service. See full design doc for details (already submitted as Assignment 1).

## ✅ What's Already Done

### Infrastructure (local, Docker Compose)
- `docker-compose.yml` orchestrates: `postgres` (pgvector/pgvector:pg16), `postgres_airflow` (separate DB for Airflow metadata), `minio` (S3-compatible local storage), `api` (FastAPI), `airflow-init` + `airflow-webserver` + `airflow-scheduler` (Airflow **2.9.0** — pinned after Airflow 3.x proved too unstable for local dev: command renames, auth changes, migration errors).
- `Dockerfile` builds the API service using `uv` for dependency management, downloads the Hotaling cocktail dataset from Kaggle at build time (via `kaggle` CLI with credentials passed as build args from `.env`, written to `/root/.kaggle/kaggle.json`).
- `.env` holds: `KAGGLE_USERNAME`, `KAGGLE_KEY`, `GUEST_BOT_TOKEN`, `ADMIN_BOT_TOKEN` (tokens already obtained from BotFather, not yet wired into code).

### Data layer
- Dataset: **Hotaling & Co. cocktail dataset** (`shuyangli94/cocktails-hotaling-co` on Kaggle — note: this is the correct dataset ID, an earlier wrong ID `hotaling/cocktail-dataset` caused 403 errors). 687 cocktails loaded.
- `services/db.py` — connection handling + schema init. Tables so far:
  - `cocktails` (id, name, category, ingredients, garnish, instructions, flavor_description, embedding vector(384))
  - `users` (id BIGINT = Telegram chat_id, name, preferences_text, embedding vector(384))
  - `orders` (id, user_id FK, cocktail_id FK, preferences, created_at, status)
  - `feedback` (id, user_id FK, cocktail_id FK, created_at) — logs "👎 Not for me" taps from the guest bot
  - `inventory` (id, ingredient_name, quantity NUMERIC, unit, updated_at) — unique index on `LOWER(ingredient_name)` so names are case-insensitively deduped (retyping "vodka" after "Vodka" updates the same row, doesn't create a duplicate)
- `services/data_loader.py` — loads Hotaling CSV into `cocktails` table (raw recipe fields only — `flavor_description` and `embedding` stay NULL until the steps below run).
- `services/flavor.py` — **new**: backfills `flavor_description` for any cocktail where it's NULL, via an LLM call (OpenAI `gpt-4o-mini` by default, `services/flavor.py:describe_flavor()`) that turns the raw recipe (name + ingredients + garnish + instructions) into a 2-3 sentence flavor/style paragraph (spirit character, sweet/bitter/sour, strength, body, mood/occasion). Added because the recommendation embeddings were previously built from pure recipe text with zero flavor vocabulary, so guest preference paragraphs (which are flavor/mood language, see `services/bot/llm_openai.py`) matched poorly — 3 of 5 recommendations in one test skewed toward strong/dry/stirred classics despite the guest describing a "refreshing, smooth, balanced" mood. `generate_flavor_descriptions()` commits per-row (network calls can fail mid-batch; resumable via the same `IS NULL` filter on restart).
- `services/embedder.py` — generates embeddings via `sentence-transformers` (`all-MiniLM-L6-v2`) for all cocktails, stores in pgvector. Uses tqdm progress bar. Text built from name+ingredients+garnish+instructions+**flavor_description** (`build_cocktail_text()`), so flavor generation must run *before* embedding generation for a given cocktail.
- `services/users.py` — `onboard_user()` encodes free-text preferences into a 384-dim embedding and upserts into `users`; `get_user_profile()` fetches back both the raw `preferences_text` and the embedding (raw text needed by the LLM re-ranker below, not just the vector).
- `services/recommender.py` + `services/recommend_llm.py` — **two-stage recommendation**: `recommend()` first pulls a candidate pool of `max(20, top_k*4)` cocktails via plain pgvector cosine similarity (`ORDER BY embedding <=> %s::vector`), then `recommend_llm.select_cocktails()` (OpenAI, tool-call forced to `select_cocktails`) re-ranks/picks the best `top_k` from that pool using the guest's raw preference paragraph + each candidate's name/flavor_description. Falls back to the plain cosine top-`k` (first `k` of the candidate pool) if the LLM call throws for any reason — `recommend()` never hard-fails just because the re-rank step did.
  - **Why**: pure top-5 cosine search kept surfacing the same handful of cocktails (e.g. "Aviation (Adapted)") across unrelated guest moods, and duplicate/near-duplicate dataset rows (e.g. "Windtalker" / "The Windtalker") both landing in the same top-5 — a hubness problem inherent to plain nearest-neighbor search that no amount of prompt-tuning on the embedding side fixes. Giving an LLM the wider shortlist lets it reason about actual fit and explicitly avoid recommending near-duplicates, at the cost of one extra LLM call per `/recommend` request.
  - **`exclude_ids`** — `/recommend` accepts an optional list of cocktail IDs to exclude from the candidate pool query. The guest bot tracks every cocktail id it has shown a chat this session in `context.user_data["shown_cocktail_ids"]` (in-memory, resets on bot restart — deliberately kept per-session rather than a DB table) and passes it on every call, so pressing "🍹 Recommend me something" repeatedly rotates through the ranked list instead of returning the same top-5 every time. Same tracking set is shared with the "Help me decide" QA flow's final recommendation, so the two entry points don't repeat each other's picks within a session either.
- **QA flow scales to how direct the guest already is** — the system prompt (`llm_openai.py`/`llm.py`, kept in sync) defaults to the playful, indirect mood-discovery questions, but has an explicit exception: if the guest's opening message already names a spirit/cocktail/clear flavor direction (e.g. "I want a whisky cocktail"), it should ask at most 1-2 direct clarifying questions instead of running the full flow, then `finish`. `MAX_TURNS` (6) is still the hard ceiling regardless of which mode it's in.
- **The durable profile is only written by: (a) a guest's first-ever "Help me decide" session, or (b) placing an order.** Repeat "Help me decide" sessions are session-only — they inform *this* round of recommendations but no longer overwrite `users.preferences_text`/`embedding`. Rationale: explicit self-reported answers in a QA session are a weaker, noisier signal than what someone actually orders, so behavior (orders) should drive the long-term profile, not repeated re-interrogation. See the two mechanisms below.
  - **First-entry bootstrap vs. session-only QA** — `services/bot/handlers/guest.py:_start_qa()` calls `GET /users/{user_id}` and stores `is_first_entry = (user does not exist yet)` in `context.user_data`. In `_ask_next_question`'s `finish` branch: if `is_first_entry`, call `onboard()` as before (this is the only way a profile gets created). Otherwise, skip `onboard()` entirely and call the new `POST /recommend/session` endpoint (`services/recommend_llm` reused, `services/recommender.py:recommend_from_text()`) which embeds the session's `preferences_summary` on the fly via `services/users.py:embed_preferences()` and runs the same candidate-pool + LLM re-rank — without ever touching the DB. `known_preferences` (fetched the same way) is still passed into the QA conversation regardless of first-entry status, so the questions stay informed either way; only the *write* is gated.
  - **Order-triggered profile update** — `services/profile_update.py` (new): `update_profile_from_order_placement(user_id, cocktail_id, order_preferences)` fetches the guest's current profile + the ordered cocktail's `flavor_description`, calls an LLM (`update_profile_from_order()`) to rewrite the profile paragraph incorporating the order as a real taste signal (reinforcing what it confirms, adjusting what it contradicts), then calls `onboard_user()` with the result. Triggered from `main.py`'s `POST /order` via `BackgroundTasks.add_task(...)` — runs *after* the response is sent, so it never delays the guest's order confirmation, and any failure is caught and logged, never surfaced to the guest or the order itself (the order is already committed by the time this runs). Fires on every order placement, not just `completed` status — a guest choosing to order something is already a signal, independent of whether the host fulfills it.
- **Inventory (stock tracking) — admin-only, manual, first phase of the deferred inventory feature.** `services/inventory.py`: `upsert_ingredient(name, quantity, unit=None)` (case-insensitive upsert-by-name), `list_inventory()`, `remove_ingredient(name)` — "remove" doesn't delete the row, it sets `quantity` to 0 so a discontinued ingredient stays visible as out-of-stock rather than disappearing. Endpoints: `GET /inventory`, `POST /inventory` (upsert), `POST /inventory/remove` — these stay "dumb": they persist whatever `(name, quantity, unit)` they're given, no interpretation server-side. Admin bot: new "📦 Inventory" button (3rd row on `admin_reply_keyboard()`) + `/inventory` command open an inline View/Update/Remove menu (`inventory_action_keyboard()`, callback pattern `^inv:`). "Update"/"Remove" set `context.user_data["awaiting"]` (the first use of this pattern in `admin.py` — previously only `guest.py` had multi-turn free-text state) and expect exactly **one** follow-up message, then auto-clear — not a continuing batch mode. Every other button handler (`cmd_orders` etc.) clears `awaiting` on entry, so tapping away mid-flow can't cause a later unrelated message to be misread as inventory input. **Not yet connected to anything else** — `cocktails`/`orders` don't reference `inventory` at all; this is pure admin bookkeeping until the substitution/feasibility features (below) are built on top of it.
  - **Unit normalization is LLM-driven, not regex** (`services/bot/inventory_llm.py`, bot-layer like `llm_openai.py` — not `services/`, since this interprets a raw Telegram message, same rationale as the guest QA LLM living in `services/bot/`). The first version of this feature used a deterministic `Name: quantity unit` line parser, but that stored whatever unit the admin typed verbatim (e.g. "3 bottles") with no actual volume — useless for future stock-math (recommend-feasibility checks, auto-decrement) that needs to compare/sum real quantities. Replaced with `parse_inventory_updates(text)` (batch, multiple ingredients per free-text message) and `parse_quantity(name, text)` (single ingredient, name already known) — both OpenAI tool-calls forced to a schema of `{quantity, unit: "ml"|"count", note?}`. The model normalizes informal containers to milliliters using standard sizes (bottle≈750ml, handle≈1750ml, fifth≈750ml, 1L=1000ml, 1 US fl oz≈29.57ml) when the admin doesn't specify an exact size, and reports the assumption in `note` (shown back in the confirmation message, e.g. "Vodka: 1500 ml (assumed 750ml/bottle)") so a wrong guess is visible and correctable. Discrete/countable ingredients (fruit, garnish, jars) get `unit="count"`, no conversion. `parallel_tool_calls=False` is set on both calls — same fix as the guest QA bug, prevents the model silently returning more than one tool call per turn.
  - **Comprehensive ingredient picker** — tapping "✏️ Update stock" now also shows every existing ingredient as an inline button (`inventory_list_keyboard()`, one per row, paginated at 8/page with ◀ Prev / Next ▶ — deliberately not capped/truncated, per "comprehensive": a long list just paginates rather than silently dropping ingredients), plus a trailing "➕ Add new ingredient" row. Tapping an existing ingredient (`invpick:{id}` → `handle_inventory_pick`) sets `awaiting = "inventory_update_single"` + remembers the name in `context.user_data["pending_ingredient"]`, then asks "What's the new amount for X?" — the reply goes through `parse_quantity(name, text)` (name already fixed, so the model only extracts the amount) via `_handle_inventory_update_single_text`. Tapping "➕ Add new ingredient" (`invaddnew` → `handle_inventory_add_new`) just re-primes the same free-text `awaiting = "inventory_update"` state with a prompt — it doesn't need its own logic, since the free-text batch parser already handles brand-new names fine (`upsert_ingredient` inserts if the name doesn't exist); the button exists purely to make that path discoverable. Free-text batch update (typing `"2 bottles of vodka"` directly, no button tap needed) still works side-by-side throughout — buttons are an added fast path, never a replacement.
  - **Remove now has the same picker, mirrored** — `inventory_list_keyboard()` was generalized to accept `pick_prefix`/`page_prefix`/`extra_rows` so the same function renders both flows without duplicating pagination logic. Remove's picker uses `invrmpick:{id}`/`invrmpage:{n}` (distinct prefixes from update's `invpick:`/`invpage:`, so the two flows' taps can never cross-route) and has no "add new" row, since removing a nonexistent ingredient is meaningless. Unlike update, tapping an ingredient here (`handle_inventory_remove_pick`) removes it immediately (no follow-up amount needed — "remove" is a fixed action) rather than setting an awaiting state.
- **Feasibility filtering — recommendations are now restricted to makeable cocktails, strict model.** Two new pieces:
  - `services/required_ingredients.py` (API layer, like `flavor.py`): backfills a new `cocktails.required_ingredients TEXT[]` column (idempotent `IS NULL` pattern, runs in `main.py`'s lifespan right after `generate_flavor_descriptions()`). One LLM call per cocktail extracts a generalized, brand-stripped ingredient list from the free-text recipe (e.g. "No.3 London Dry Gin" → "gin") — generalized specifically so it can later be fuzzy-matched against whatever the admin actually tracks in `inventory`, since the two were never linked. Excludes always-available basics (ice, water) that aren't worth gating on.
  - `services/recommender.py:_infeasible_cocktail_ids()`: for every cocktail with `required_ingredients` populated, checks whether *every* required term has a case-insensitive substring match against an `inventory` entry with `quantity > 0`. If even one required ingredient has no match, the cocktail is infeasible. The infeasible ID list is unioned into the existing `exclude_ids` mechanism (originally built for recommendation variety) and passed straight into the candidate-pool SQL query — no schema/query duplication needed. Applies to both `recommend()` and `recommend_from_text()` automatically, since both share `_recommend_with_profile()`.
  - **Deliberately strict, not lenient**: a required ingredient must be tracked in `inventory` with a positive quantity to count as available — an ingredient never entered into `inventory` at all is treated as *unavailable*, not "assume it's fine." This was a real design fork (see chat history) — the lenient alternative (only exclude on an explicit `quantity = 0`, treat untracked as available) would have degraded more gracefully on a sparse/empty inventory, but was rejected because the plan is to fully populate `inventory` up front, so strict filtering is the actually-correct behavior rather than a safety compromise.
  - **Consequence worth knowing**: since `inventory` starts empty, this filter returns *zero* feasible cocktails until the admin populates it — `guest.py:_send_recommendations()` now sends "Sorry, nothing matches what's currently in stock" instead of silently returning no cards when `results` is empty, so this doesn't look like a broken bot during that window.
- **Admin bot allowlist** — `services/bot/handlers/auth.py` (new): `ADMIN_USER_IDS` env var (comma-separated Telegram user IDs), checked via an `admin_only()` decorator wrapped around every handler at registration time in `admin_main.py` (not repeated inside `handlers/admin.py` itself). Fails **open** (allows everyone) if `ADMIN_USER_IDS` is unset — deliberate, so a fresh deploy can't lock the admin out before they've set it — and fails **closed** (rejects anyone not listed) once it has at least one ID. Defaults to the same value as the existing `ADMIN_CHAT_ID`.
- **"Users" is a 3-level drill-down (guest picker → guest summary → manage), not a global stats dump — redesigned once already.** First cut showed global "latest orders across everyone" + global "most popular cocktails" immediately on tapping Users, plus a separate "Manage guest" button to reach an individual guest. That read as confusing/unclear once actually used (a global feed doesn't answer "how's *this* guest doing"), so it was replaced:
  - Tapping "👥 Users" goes **straight to a paginated guest picker** (`cmd_users`, reusing `inventory_list_keyboard()`, `pick_prefix="guestpick"`) — no intermediate stats screen.
  - Picking a guest (`handle_guest_pick`) shows **that guest's own last 5 orders + their personal top 3 most-ordered cocktails** in one message (`services/orders.py:list_orders_for_user()` / `popular_cocktails_for_user()`, both `WHERE orders.user_id = %s` — per-guest, not global), plus a "⚙️ Manage guest" button.
  - Tapping "Manage guest" (`handle_guest_manage`, new — this is what `handle_guest_pick` used to do directly) shows the guest's raw preferences text with a "🧹 Clear preferences" button (`services/users.py:clear_preferences()` — sets both `preferences_text` and `embedding` to `NULL`, still requires the matching `recommend()` fix below).
  - **Required a matching fix in `recommend()`**: since a cleared-but-existing user now has a NULL embedding, `recommend()` treats `preferences_text IS NULL` the same as "user not found" (re-onboarding required) instead of crashing the pgvector `<=>` query on a NULL vector.
  - The global versions (`_users_text()`, `services/orders.py:popular_cocktails()`, `GET /cocktails/popular`, `users_stats_keyboard()`, `usermanage` callback/`handle_user_manage`) were deleted outright rather than kept around unused — nothing else referenced them (confirmed via grep before removing). If a global "what's trending across the whole party" view is wanted later, it's a small addition, just not this same code path.
  - **Back buttons added at both drill-down levels, reusing existing callbacks rather than adding new views.** The guest summary (`guest_summary_keyboard()`) has "◀ Back to guest list" (`guestlist` callback → `handle_guest_list_back`); the preferences/manage view (`guest_detail_keyboard()`) has "◀ Back" wired to `guestpick:{user_id}` — the *same* callback data the guest-list picker uses, so it needed zero new handler, it just re-runs `handle_guest_pick()`.
  - **Follow-up fix: adding back-and-forth navigation immediately re-triggered the flooding problem, just one level down** — browsing guest list → guest → back → another guest → manage → back, etc. was sending a brand new message on every single hop, same failure mode as before the main-menu clean-sheet fix, just inside the Users sub-flow this time (which deliberately doesn't trigger `_clear_menu()`, since that's reserved for main-menu switches). Fixed properly this time by converting the whole guest drill-down to **edit the existing message in place** instead of sending new ones — `handle_guest_pick`, `handle_guest_manage`, `handle_guest_clear`, and `handle_guest_list_back` all now call `query.edit_message_text(...)` (same message id throughout: list ⇄ summary ⇄ preferences), rather than `_reply()`. This is the standard Telegram bot pattern for drill-down navigation (`handle_guest_page`'s pagination was already doing this via `edit_message_reply_markup` — just not extended to full content swaps until now) and is a better fix than message tracking/deletion for this kind of back-and-forth: zero new messages accumulate no matter how many times the admin bounces between guests. `handle_guest_clear` also now re-renders the preferences view showing the cleared state (`"Preferences: (none)"`) in place, rather than a one-off confirmation line that would've orphaned the guest_detail_keyboard buttons.
  - `_guest_list_content()` (new, plain function returning `(text, keyboard)`) replaces the old `_send_guest_list()` — factored out so `cmd_users` (first entry, must send a *new* message since there's nothing to edit yet coming from a plain text button tap) and `handle_guest_list_back` (must edit) can share the content-building logic while differing in how they deliver it.
  - **Same structural issue likely exists in the Inventory and Manual-order sub-flows** (category pick → item pick → prompt also sends a new message per hop) — not converted yet since it wasn't reported as a problem there, but the fix would be the same pattern if it comes up.
- **The entire order notification is now generated by a single LLM call at order time, not assembled from cached/raw fields — went through two iterations to land here.**
  - **Iteration 1** (superseded): a catalog-wide backfill cached one origin story per cocktail (`cocktails.origin_story`, generated once, reused by every future order of that cocktail), and ingredient/instruction lists were formatted deterministically from the raw dataset text (`services/format_recipe.py`, comma/sentence splitting).
  - **Why it changed**: two problems with iteration 1. (a) **Unit mismatch** — the dataset's recipe amounts are in oz, but `inventory` is tracked in ml, so the admin's order notification and their stock view used different measuring systems for the same ingredient. (b) **No path to multi-language** — a planned future feature (switch the bot's language) doesn't work with a story cached once, in one language, at catalog-load time; it needs to be generated fresh per order so the language can vary per request later.
  - **Current design**: `services/order_message.py` (new, forced tool-call, same pattern as every other LLM call site) takes the raw cocktail recipe and returns three things in one call: `ingredients` (array, liquid pours converted oz→ml to match inventory units, non-liquid items like dashes/garnish left as-is), `instructions` (array of numbered steps), and `story` (2-4 sentence cocktail history/legend/myth — explicitly instructed not to fabricate specific facts as certain when no real history is known). `place_order()` calls this once per order (not per cocktail in the catalog — cost scales with order volume during a party, not with the 687-row dataset) and **persists the result on the `orders` row** (`ingredients_text`, `instructions_text`, `story_text` columns) rather than the `cocktails` table, since it's now order-specific (unit conversion happened fresh, and future language variation would make catalog-wide caching wrong anyway). Wrapped in try/except with a fallback to the old deterministic `format_recipe.py` splitting (no story) if the LLM call fails — order placement itself never blocks on this.
  - `services/bot/handlers/admin.py:_order_text()` (Orders/History views) and `services/orders.py:list_recent_orders()` now read straight from the stored `orders.ingredients_text/instructions_text/story_text` — no reformatting or recomputation on every view, and the displayed recipe is guaranteed to match exactly what was sent in the original notification (garnish still comes from `cocktails.garnish` directly since it's not a measured/converted quantity).
  - **The personalized "how it feels" guest-facing blurb lives in the recommendation flow instead**, unaffected by this change: `services/recommend_llm.py:select_cocktails()` returns `[{"id", "vibe"}, ...]` — the vibe blurb is generated *in the same tool call* that already re-ranks the candidate shortlist, so recommending top-5 still costs one LLM call total, not six. (Also fixed a latent bug while touching this file: `parallel_tool_calls=False` was missing here, unlike every other tool-call site — same class of bug as the original QA multi-tool-call crash.) `services/recommender.py:_to_result()` carries `vibe` through the API response; `guest.py:_send_recommendations()` appends it under the ingredients list (still deterministically formatted via `format_recipe.py`, since that path is catalog-wide and oz is a normal unit for a guest-facing menu — no mismatch to fix there).
  - Notification formatting still uses Telegram **HTML** `parse_mode` (bold section headers, italic story) — chosen over MarkdownV2 because MarkdownV2 requires escaping `. - ( )` etc. that appear constantly in real recipe text, while HTML only needs `< > &` escaped. Guest-controlled fields (`guest_name`, order `preferences`) are `html.escape()`'d.
  - **Known follow-up, not yet fixed**: the 🔄 Adapt Recipe button (`services/recipe_adapt.py`) still substitutes against the *raw* `cocktails.ingredients` (oz), not the order's unit-normalized `ingredients_text` — so an adapted recipe can show oz again on the same order that showed ml. Low priority since Adapt Recipe is tapped occasionally, not on every order, but worth reconciling if the unit mismatch resurfaces there.
  - **Adapt Recipe now also checks real inventory when picking a substitute — it didn't before, same class of gap as the order-preference one above, just not caught at the same time.** It always correctly *detected* what's missing (`required_ingredients` vs. `available_ingredient_terms()`), but `adapt_recipe()`'s prompt only ever told the LLM what was missing, never what was actually in stock to replace it with — so it could suggest a substitute that also wasn't in the bar. Fixed the same way: `adapt_order_recipe()` now passes `available_ingredient_terms()` into `adapt_recipe()` as a sixth argument, and the system prompt requires picking from that list when a reasonable option exists there (falling back to "not in stock — needs sourcing" in the summary otherwise).
  - **Guest order-time preferences now actually adjust the recipe, not just get displayed as a note.** Previously `preferences` (the free-text "not too bitter"/"less sweet" a guest can attach when ordering) was stored and shown to the admin verbatim, but never changed the ingredients/instructions — easy to miss since the unrelated Adapt Recipe button *does* change ingredients, just for a different reason (out-of-stock substitution, not taste). `generate_order_message()` now takes `preferences` as a fourth argument and, when present, is instructed to tweak quantities/substitutions/steps to honor it (favoring small amount changes over swapping core spirits) and summarize what changed in a new `adjustments` field — surfaced as an italic "Adjusted: ..." line under the preferences line, both in the order notification and in Orders/History (new `orders.adjustments_text` column, same store-once/read-back pattern as `ingredients_text`/`instructions_text`/`story_text`). Only populated when the guest actually gave preferences; the fallback path (LLM call fails) leaves it `None`, same as `story_text`.
    - **Preference-driven substitutions check real inventory, same as Adapt Recipe does.** First cut of this didn't — a guest allergy test (`"I am allergic to honey"` on a recipe using honey syrup) got substituted with agave syrup purely from the model's general bartending knowledge, with no idea whether the bar actually has agave syrup. Fixed by passing `available_ingredient_terms()` (the same in-stock-name list `services/inventory.py`/feasibility filtering/Adapt Recipe already use) into `generate_order_message()` as a fifth argument, only fetched/sent when `preferences` is present (no cost on the common no-preference path). The system prompt now requires picking a substitute from that stock list when a reasonable one exists there, and explicitly saying "not in stock — needs sourcing" in `adjustments` if it has to reach outside it — so the bartender is never quietly told to use something that isn't actually behind the bar.
    - **Order ingredients are genuinely structured, not a free-text line per ingredient** — `OrderMessage.ingredients` (see the Pydantic section below) is `list[{name, quantity, unit}]`, `unit` constrained to the same `"ml"|"count"` enum `inventory` already uses, not a display string the LLM composed itself. `place_order()` builds the human-readable bullet list from this (`_format_ingredient_line()`) and *also* persists the raw structured array as `orders.ingredients_json` (TEXT column holding a JSON-encoded list, matching this project's plain-SQL-no-ORM style).
    - **oz→ml conversion rounds to jigger increments now, not mathematically precise decimals.** The LLM was converting using the exact 29.5735 ml/oz factor, producing amounts like "14.79 ml Lime Juice" — technically correct but useless against real bar equipment, which is marked in round numbers. Fixed with a shared `JIGGER_RULES` constant in `services/models.py` (used by both `OrderIngredient.unit`'s field description and `UNIT_RULES`, replacing the two previously-inconsistent conversion factors — one said 30ml/oz, the other 29.57ml/oz): spells out the standard bartending shorthand (0.25 oz = 7.5 ml, 0.5 oz = 15 ml, 0.75 oz = 22.5 ml, 1 oz = 30 ml, etc.) and instructs rounding anything else to the nearest 2.5 ml, explicitly forbidding unrounded decimals. Since Pydantic field descriptions become part of the JSON schema sent to the model, this guidance shapes how `quantity` gets filled even though it's attached to the sibling `unit` field — same mechanism the original (less precise) instruction already relied on, just corrected text.
    - **Inventory now decrements automatically when an order is marked completed.** `services/inventory.py:resolve_inventory_name(name, items)` fuzzy-matches (case-insensitive, bidirectional substring — same rule `missing_ingredients()` uses) an ingredient name against real `inventory` rows and returns the *actual* stored name, or `None` if nothing matches; `decrement_for_order(ingredients)` runs that resolution per ingredient and calls `upsert_ingredient(matched_name, quantity, unit, mode="subtract")` only for matches, returning the unmatched names (untracked ingredients like garnish nobody inventoried, or fresh sourcing) for logging rather than erroring. This resolution step exists specifically because `upsert_ingredient`'s `ON CONFLICT` match is exact, not fuzzy — passing an LLM-phrased name like "Gin" straight through when the real row is "No.3 London Dry Gin" would silently create a phantom "Gin" row at quantity 0 instead of decrementing the real one.
      - Triggered from `services/orders.py:update_order_status()`: fetches the order's previous `status` + `ingredients_json` before updating, and only decrements when the new status is `"completed"` **and** the previous status wasn't already `"completed"` (guards against double-decrementing if the same order is somehow marked complete twice) **and** `ingredients_json` is present (orders that hit the fallback path at placement time — LLM call failed — have no structured data to decrement from, and are silently skipped rather than erroring). Wrapped in try/except so a decrement failure never blocks the status update itself, which has already committed by that point anyway.
      - Whatever was actually poured is what gets decremented — since `ingredients_json` is populated from the *same* `OrderMessage` that already applied preference-driven substitutions (e.g. the honey→agave swap), a guest's allergy substitution correctly draws down agave stock, not honey stock, with no separate bookkeeping needed.
      - `cancelled` orders never decrement (nothing was poured); `in_progress` doesn't either (only the terminal `completed` transition does) — consistent with "the drink was actually made" being the real-world event this represents.
- **Every LLM tool-call schema in the project is now a Pydantic model, centralized in `services/models.py`, instead of 8 hand-written JSON-schema dicts scattered one per file.** Each call site builds its tool definition via `openai.pydantic_function_tool(SomeModel, name=..., description=...)` and parses the response with `SomeModel.model_validate_json(response.choices[0].message.tool_calls[0].function.arguments)` instead of `json.loads()` into a bare dict — every downstream consumer now uses attribute access (`result.adapted_ingredients`) instead of key access (`result["adapted_ingredients"]`), which is why `orders.py`, `recommender.py`, and `admin.py`'s inventory handlers all changed alongside the LLM modules themselves. Converted: `order_message.py` (`OrderMessage`/`OrderIngredient`), `recipe_adapt.py` (`AdaptedRecipe`), `recommend_llm.py` (`CocktailSelection`/`CocktailPick`), `required_ingredients.py` (`RequiredIngredients`), `inventory_categorize.py` (`InventoryCategory`), `bot/inventory_llm.py` (`InventoryUpdateBatch`/`InventoryUpdateItem`/`InventoryQuantity`), `bot/llm_openai.py` (`AskQuestion`/`FinishQA`, two tools dispatched by name in `next_turn()`). **Not converted**: `services/bot/llm.py` (the Anthropic-flavored QA mirror) — confirmed via grep that nothing imports it (`guest.py` only uses `llm_openai`), so it's dead code, out of scope for this pass. Also not converted: `flavor.py` and `profile_update.py`, which were never tool-calls to begin with (plain chat completions returning freeform text) — nothing to structure there.
  - **Why the schema descriptions changed from "omit if unset" to "null if unset"**: OpenAI's structured-outputs strict mode (which `pydantic_function_tool` opts into automatically) requires every property to appear in `required`, including optional ones — an `Optional[str] = None` field becomes `anyOf: [string, null]` and *must* be present in the response, just possibly `null`, rather than being omittable the way the old hand-written schemas allowed. `MODE_RULES`/`adjustments`'s field descriptions were reworded accordingly (`services/models.py`).
  - `pydantic` is now an explicit `pyproject.toml` dependency (was only ever pulled in transitively via `fastapi` before).
- **Every main-menu button now starts with a clean sheet — old menu clutter gets swept away, not left to accumulate.** The admin chat was flooding fast from repeated navigation (checking Orders/Users/Inventory, paging through pickers, follow-up prompts). `admin.py` gained two small helpers: `_reply(context, sendable, text, **kwargs)` — a drop-in replacement for `sendable.reply_text(...)` that also appends the sent message's id to `context.user_data["menu_message_ids"]` — and `_clear_menu(update, context)` — pops that whole list and deletes every message in it (each wrapped in try/except, since some may already be gone, e.g. via the completed/cancelled-order deletion above). Every `.reply_text(...)` call in the file was switched to `_reply(...)` *except* `handle_adapt_recipe`'s three replies, deliberately left untouched.
  - **Where clearing is triggered vs. what gets cleared, and why they're different scopes**: `_clear_menu()` is only *called* from the 6 top-level handlers (`cmd_orders`, `cmd_history`, `cmd_cocktails`, `cmd_users`, `cmd_inventory`, `cmd_manual_order`) plus `start` — tapping a sub-navigation button (an inventory category, a guest picker page, "Manage guest") never triggers a clear. But *tracking* (`_reply`) is used everywhere in those sub-flows too, not just the top-level entry message. So the practical effect: browsing Inventory → Update → a category → an ingredient → typing an amount can pile up 4-5 messages with zero clearing in between (sub-navigation is left alone, as agreed), but the moment the admin taps any *other* main-menu button, that entire accumulated trail gets deleted at once, along with whatever the previous top-level view was. This is what actually solves the flooding — clearing only the single top-level message and leaving sub-flow trails behind would have left most of the actual clutter in place.
  - **Why `handle_adapt_recipe` is excluded**: an adapted recipe is operationally important mid-drink (the bartender may still need to read it while pouring), not menu-navigation clutter — sweeping it away just because the admin tapped a menu button afterward would be actively harmful, unlike sweeping away an old Inventory listing. Same reasoning kept `handle_order_status`'s edits/deletes (the order notification thread itself) out of this tracking system entirely — it's event history, not navigation.
  - **Follow-up fix: the bottom persistent reply keyboard (Orders/History/Cocktails/Users/Inventory/New order buttons) stopped reliably reappearing after this shipped.** Several top-level handlers (`cmd_orders`/`cmd_history` via `_send_orders`, `cmd_cocktails`, `cmd_users`, `cmd_inventory`, `cmd_manual_order`) never actually re-attached `admin_reply_keyboard()` to any of their messages — they relied entirely on it having been set once (at `/start`, or by the free-text handlers that already had this fix from earlier in the session) and staying put client-side. That assumption got shakier once `_clear_menu()` started deleting the messages that had originally set it. Fixed by making every top-level handler explicitly re-attach `admin_reply_keyboard()` to at least one of its own messages: `_send_orders()` puts it on the initial "N order(s):"/empty-state message (the per-order messages still need their own `order_status_keyboard()` inline markup, and Telegram only allows one `reply_markup` per message — inline and reply-keyboard can't share one message). `cmd_users`/`cmd_inventory`/`cmd_manual_order` — whose main content already needs an inline keyboard (`users_stats_keyboard()`/`inventory_action_keyboard()`/the guest picker) — now send a short header message first (`"👤 Manage a guest:"` becomes the users-view label, `"📦 Inventory"`, `"🧾 New order"`) carrying the reply keyboard, then their inline-keyboard content as a second message. `cmd_cocktails` just got the reply_markup added directly (it had never carried any `reply_markup` at all, reply-keyboard or otherwise — a pre-existing oversight, not a regression from this change).
- **Completed/cancelled orders now delete their Telegram message instead of leaving an edited "Status: ✕ Cancelled" line behind** — `admin.py:handle_order_status()`: for `completed`/`cancelled`, calls `query.message.delete()` (works for a bot's own messages in a private chat) instead of `edit_message_text`, falling back to the old edit-with-status behavior (keyboard removed) if deletion ever fails. `in_progress` still edits normally, since that order is still active and the admin needs to keep seeing it. Applies uniformly whether the button lives on the original order notification or on a message from the 📋 Orders list, since both route through the same handler. Reduces chat clutter — the order is still fully recorded and viewable in 🧾 History, which renders fresh from the DB independent of whether the live notification message still exists.
- **🧾 History is now day-scoped with Previous/Next-day navigation, instead of dumping the last 20 completed/cancelled orders regardless of when they happened.** `services/orders.py:list_recent_orders()` gained an optional `date` param (`WHERE orders.created_at::date = %s`, plain SQL date-cast, no new column) — threaded through `GET /orders/recent?date=`, `api_client.recent_orders(date=...)`, unchanged for every other caller since it defaults to `None`. `admin.py:cmd_history()` defaults to `date.today()`; a new `services/bot/keyboards.py:history_nav_keyboard(prev_date, next_date=None)` renders "◀ Previous day"/"Next day ▶" **side by side in one row** (Telegram inline keyboards are just a list of button-lists — one row per inner list — same technique `order_status_keyboard()` already used for Start/Cancel; nothing special needed to put buttons next to each other rather than stacked). "Next day" is only shown when *not* viewing today (no next-day to go to otherwise). Tapping a nav button (`historyday:{date}` → `handle_history_day`) re-renders for that date.
  - **Day navigation clears the previous day's messages before showing the new one** (`_clear_menu()`, the same mechanism used for main-menu switches) rather than editing in place — unlike the guest drill-down fix above, a day's worth of orders is a variable-length batch of messages (0 to many), which can't be cleanly "edited into" a different day's batch of a different length. Delete-and-resend is the right tool here specifically because the content is list-shaped, not a single evolving view.
  - **Follow-up: dropped the separate "📅 {label}" message and put dates on the button labels instead.** Nav buttons now read `"◀ Jul 03"` / `"Jul 05 ▶"` (`history_nav_keyboard()` takes `date` objects and formats via `strftime("%b %d")` for the label while still using `.isoformat()` for the callback data — display and wire format decoupled) rather than generic "Previous day"/"Next day" text, and rather than sending them as their own trailing message, they're attached via `last_message.edit_reply_markup(...)` to whatever the *last* message `_send_orders()` already sent that day (the last order, or the empty-state message if there were none) — one fewer message per day view. This only works because History's per-order messages carry no `reply_markup` of their own (`include_status=True` → `order_status_keyboard()` isn't attached, unlike the Orders view), so there's nothing to clobber by adding one via edit. `_send_orders()` now returns the last message it sent (via `_reply()`'s existing return value) specifically so callers like `_show_history_day()` can do this; `cmd_orders()` still calls it the same way and just ignores the return.
- **Inventory updates now support add/subtract, not just overwrite.** `services/bot/inventory_llm.py`'s tool schemas gained a `mode: "set"|"add"|"subtract"` field (LLM-inferred from phrasing — "add 2L of orange juice" → `add`, "used up 300ml" → `subtract`, a plain amount statement → `set`, the pre-existing behavior, still the default when the field is omitted). `services/inventory.py:upsert_ingredient()` branches its `ON CONFLICT` SQL by mode; `subtract` uses `GREATEST(0, ...)` so stock can't go negative. This is the same free-text box as before — no new UI, the flexibility is entirely in how the LLM parses what's typed.
- **Inventory is now browsed by category instead of one flat alphabetical list.** New `inventory.category TEXT` column, fixed list (`Base Spirits`, `Liqueurs`, `Bitters`, `Juices`, `Syrups & Sweeteners`, `Garnishes`, `Mixers`, `Other`) categorized by `services/inventory_categorize.py` (idempotent `WHERE category IS NULL` backfill, same shape as `required_ingredients.py`, runs in `main.py`'s lifespan). New ingredients get categorized **inline at upsert time** (in `admin.py`, via `_resolve_category()`) rather than left NULL until the next restart — inventory is browsed live during a party, so a same-session addition sitting uncategorized would be visibly broken. View/Update/Remove now all show a category picker (`category_picker_keyboard()`, new in `keyboards.py`) as the first step before the existing paginated item picker — the one nontrivial part was making `inventory_list_keyboard()`'s pagination category-aware, since its `page_prefix` is a flat string: callback data became `invpage:{category}:{n}` and the page handlers now split into 3 parts instead of 2. The free-text batch-update box is untouched and still works without ever touching a category picker.
- **Admin can place an order on a guest's behalf** — for guests who order verbally instead of through the app. New "🧾 New order" button starts a callback-driven flow: pick a guest (reuses the same picker shape as the Users guest-manager, different callback prefix since the flows diverge after pick) → pick a cocktail category → pick a cocktail (paginated, via new `services/recommender.py:cocktails_in_category()`) → optional free-text preferences → calls the existing `api_client.place_order()` unmodified, so the LLM story + HTML notification flow fires exactly the same as a guest-initiated order.

#### Flavor description generation — how it runs, and how it should extend

`main.py`'s lifespan handler runs, in order, on **every** API startup (not just first boot):
```
if cocktails table empty: load_hotaling_data()
generate_flavor_descriptions()      # no-op once backfilled — filters WHERE flavor_description IS NULL
generate_required_ingredients()     # no-op once backfilled — filters WHERE required_ingredients IS NULL
generate_embeddings()               # no-op once backfilled — filters WHERE embedding IS NULL
```
All three generation functions are idempotent batch backfills keyed off `IS NULL`, so they're safe (and cheap — a single empty-result query) to call unconditionally on every restart. This means **any cocktail row inserted by any future code path** gets picked up automatically the next time the API restarts, with no manual step.

This mattered for one deferred feature that's now done, and still matters for one still-deferred:
- ~~Admin "add cocktail" flow~~ — **DONE**, see the cocktail categorization/add-cocktail section above (`services/cocktails.py:create_cocktail()`) — it does exactly this: `describe_flavor()` → `extract_required_ingredients()` → `categorize_cocktail()` → embed, synchronously, right after insert.
- **Ingredient substitution pipeline** (`adapted_recipes` table, deferred): each adapted recipe is a recipe-shaped row derived from an original cocktail. It should go through the same pipeline (flavor description → required ingredients → category → embedding) before being eligible for recommendation, using the *adapted* ingredients/instructions as input — never re-deriving from another adaptation (this no-chaining rule was already a stated design constraint before the flavor pipeline existed, and now also applies to keeping flavor descriptions and required-ingredient lists accurate).

In short: the pattern going forward for "a new recommendable cocktail-like thing exists in the DB" is always *raw recipe fields → `describe_flavor()` → `flavor_description` → `build_cocktail_text()` → embed*. Nothing should write directly to `embedding` from raw ingredients alone anymore.

  - **A cocktail belongs to every category it matches, not just one** — `categorize_cocktail()` returns a list, e.g. a vodka+gin drink gets `['Gin', 'Vodka']`. This is why `categories` is `TEXT[]`, not a scalar column like the old `category` (which is left in the table, physically present but unused going forward — consistent with this project's additive-only migration style, no `DROP COLUMN`). `cocktail_summary()` groups via `unnest(categories)` so each cocktail contributes to every one of its categories' counts; `cocktails_in_category()` filters via `%s = ANY(categories)`.

Fixed by dropping modifier-only keywords entirely: `Sparkling & Champagne` only matches `champagne/prosecco/sparkling wine/cava`; `Amaro & Bitter Liqueurs` only matches specific named amari (`amaro/campari/aperol/chartreuse/fernet/cynar/suze`), not the generic word "liqueur". A Manhattan now correctly comes back as just `['Whiskey']`; a Negroni (gin, Campari, sweet vermouth) correctly comes back as `['Gin', 'Amaro & Bitter Liqueurs']` since Campari genuinely is one of its two defining characters.
  - **"🍸 Cocktails" is now a category-browsing picker**, mirroring the Inventory/Manual-order pattern: tapping it shows the count summary (now spirit-based) plus a category-button picker (`category_picker_keyboard()`, reused) with an "➕ Add cocktail" row attached. Tapping a cocktail name currently just acknowledges the tap (`handle_cocktail_view`) — no recipe detail view yet, flagged as a natural but unbuilt follow-up.
  - **Admin can add a new cocktail from free text, with the bot asking follow-up questions until it has enough.** `services/bot/cocktail_intake.py` (new, mirrors the guest QA flow's `ask_question`/`finish` dual-tool shape in `llm_openai.py`): one LLM call per turn, forced to pick between `ask_for_missing_info` (one short question when name/ingredients/instructions are missing or too vague — garnish is optional and never blocks) and `record_cocktail` (fires once there's enough, returns a `CocktailDraft`). Same `MAX_TURNS` safety cap as the guest flow, forcing a record past that point rather than looping forever.
  - **A confirm step (Save/Discard) sits between extraction and the actual write** — no delete endpoint exists for cocktails, so a misparsed recipe would otherwise sit in the catalog permanently. Tapping Save calls the new `POST /cocktails` → `services/cocktails.py:create_cocktail()`, which does the insert and then **synchronously** (not waiting for the next restart) runs the exact same enrichment pipeline `CLAUDE.md` had already sketched out for this feature before it existed: `describe_flavor()` → `extract_required_ingredients()` → `categorize_cocktail()` (the new spirit taxonomy, computed the identical way as the backfill) → embedding — so a cocktail added mid-party is immediately recommendable and correctly feasibility-filtered, not stuck waiting for a restart.

## Known Gotchas / Lessons Learned (worth preserving)

- **PowerShell vs zsh**: user develops on both Windows (PowerShell) and Mac (zsh). `curl` in PowerShell aliases to `Invoke-WebRequest` — must use `curl.exe` explicitly; line continuation is backtick on PowerShell, backslash on zsh/bash.
- **Python relative imports**: running a file directly (`uv run services/foo.py`) vs as a module (`uv run -m services.foo`) changes `sys.path` resolution — relative imports (`from .db import`) only work with `-m`. Standardized on `-m` for all script invocations.
- **Kaggle dataset ID**: correct is `shuyangli94/cocktails-hotaling-co`, not `hotaling/cocktail-dataset` (404/403 errors otherwise). Kaggle CLI auth requires `~/.kaggle/kaggle.json` (`{"username":..., "key":...}`), not plain env vars, despite some docs suggesting otherwise.
- **Airflow version**: stick with **2.9.0** for local Docker Compose dev. Airflow 3.x changes (`webserver`→`api-server` command rename, `users create` removed in favor of `_AIRFLOW_WWW_USER_CREATE` env var which still generates a random password unpredictably, separate `dag-processor`/`triggerer` services required, execution_date DB migration errors when reusing old volumes) made it too unstable for a quick class project. If revisiting Airflow 3.x, start fresh with the official `docker-compose.yaml` from `airflow.apache.org/docs/apache-airflow/<version>/docker-compose.yaml` rather than hand-rolling it.
- **Airflow + app DB conflict**: Airflow needs its own PostgreSQL database (`postgres_airflow` service, separate from the app's `postgres`/`cocktail_db`) — sharing one Postgres instance/database between the app and Airflow metadata causes schema migration failures.
- **Docker volumes persist data** — `postgres_data` volume means dataset/embeddings only need to be (re)generated once; lifespan code checks `COUNT(*)` on `cocktails` before reloading, making restarts fast and idempotent.
- **`.env` edits don't reach a running container** — `docker-compose.yml` substitutes `${VAR}` into a service's environment only at container *creation* time. Editing `.env` while the container is already running has no effect until you recreate it (`docker compose up -d <service>` — no `--build` needed if only `.env` changed, not code).
- **Telegram `sendMessage` needs the recipient to have messaged the bot first** — a bot can't push to a chat_id that has never started a conversation with it (`400: chat not found` otherwise). The admin must send any message (e.g. `/start`) to `@bar_admin_bot` once; since the Admin Bot isn't coded yet, it won't reply, but the message still registers the chat so push notifications work.
- **`notify_admin()` currently doesn't check the Telegram API response** — failures (bad token, chat not found, etc.) are silent. Worth hardening with response-status logging before relying on it for the real bots.
- **The `api` service needs `OPENAI_API_KEY` now too**, not just the bot processes — `services/flavor.py` runs inside the FastAPI lifespan (not the bot), so `OPENAI_API_KEY` was added to the `api` service's `environment:` block in `docker-compose.yml`. Same "`.env` edits don't reach a running container" rule applies — recreate the `api` container after setting it.
- **Persistent reply keyboards can disappear for two different reasons — both needed fixing**:
  1. `is_persistent=True` (now set on both `admin_reply_keyboard()` and `guest_reply_keyboard()`) stops the Telegram client from letting the user manually collapse/hide the bottom keyboard — without it, `resize_keyboard=True` alone doesn't prevent hiding.
  2. **Separately**: typing free text swaps the client to the device's system keyboard (it has to — the custom keyboard has no letter keys), and the client doesn't reliably snap back to the custom button grid on its own after sending — only when the *next* bot message explicitly re-attaches that same `reply_markup`. Fixed in `admin.py` by adding `reply_markup=admin_reply_keyboard()` to the three responses that follow the admin actually typing something (`_handle_inventory_update_text`, `_handle_inventory_update_single_text`, `_handle_inventory_remove_text`) — button-tap-triggered responses don't need this, since tapping a reply-keyboard button never invokes the system keyboard in the first place. **`guest.py` likely has the same latent issue** in its free-text-driven responses (order-preferences confirmation, QA follow-up questions) but hasn't been fixed yet — those are complicated by already needing an *inline* keyboard on the same message (options/cocktail buttons), and a message can only carry one `reply_markup`, so the fix there needs more thought than a straight copy-paste of the admin fix.
  Existing chats need one fresh message carrying the updated keyboard (e.g. `/start`) before either fix takes visible effect — neither retroactively fixes an already-open chat.
